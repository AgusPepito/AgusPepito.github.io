# Performance capture

Baseline before diagnostics: `7cdd162`. Current reports identify gate-stage profiling and exact caching as `gate-stage-cache-v3`; see `PERFORMANCE_GATE_PROFILE.md`. The v2 indexed/full-level loading behavior and cache limits remain described in `PERFORMANCE_PRELOAD_HANDOFF.md`. `worker-assets-v1` used partial streaming; older reports without a version field used synchronous generation.

Diagnostics require the developer flag `dev=1`. Open `racer.html?dev=1&perf=1`, or use `racer.html?dev=1` and press **F8** / tap **Perf** in the header. With `dev=1`, `preload=all` also opens the panel automatically. Without the developer flag, the toggle is hidden and diagnostics activation, event capture, memory measurement and log saving are disabled. The panel records frames only while enabled. **Compact** leaves the main counters visible and continues collecting all metrics. **Perf** closes the panel and stops collection, preserving the capture. **Reset** clears the capture. **Save report** downloads JSON locally; nothing is sent to a server.

## Persistent comparison log

A compact summary is saved automatically to this browser's local storage every 10 seconds of profiling, and on pause, closing the panel, Reset, export, or leaving/hiding the page. Reset saves the old capture first and starts a new one; each page reload also starts a new capture. The latest 100 captures are retained. **Save CSV** downloads this history as one row per capture, including level/mode, FPS, p95/p99/worst frame time, spike counts, peak draw calls/triangles/resources, CPU/build peaks, render resolution and browser identity. Statistics describe the retained frame window, with total/retained frame counts included.

Storage is specific to the browser and site address; phone and laptop histories are separate until their CSVs are collected. Clearing site data removes the local history. If storage is unavailable, the panel says so and can still download the current capture. Download CSVs for durable comparison; exports do not write directly into the project directory. A crash or abrupt termination may lose work since the last auto-save.

## Suggested manual capture

1. On each device, open the performance URL before loading a level to capture initial view construction. Note the device model and browser; reports include browser metadata but cannot reliably identify the exact device or GPU.
2. Drive a representative route, including detailed sections, turbo, and a checkpoint transition. Use Compact on a small screen.
3. Pause and save the report. Include the device model and any stutters you noticed when sharing it.
4. For a warm retry comparison, Reset and repeat the same route. To measure a fresh load again, reload with `?perf=1`. Retrying the same level reuses already built assets, so it is a different workload from a cold run.

The preview URL using `127.0.0.1` works on the host computer only. A phone needs a hosted copy or a preview bound to a LAN interface and its LAN address.

## Interpretation

Revision `shader-warmup-v1` calls `renderer.compileAsync` after the selected level's scene is fully attached and its lights/environment are configured. This includes hidden, distant and instanced meshes. Driving and the menu fly-through wait until compilation resolves; no scene rendering forces a compiling shader to finish synchronously. The Race button stays loading through preparation. `shader-warmup-start`, `shader-warmup-ready` and `shader-warmup-error` events record the level, duration, program counts and parallel compilation support. Frame samples include `shaderWarmupState` and `shaderWarmupMs`. This moves shader preparation into the loading wait; it does not pre-upload all geometry or pre-attach the next level. Browsers without parallel shader compilation may still block during loading. Verification for this revision is source review and production build; user captures are needed to verify the 527-metre hitch is gone.

Checkpoint handoff revision `handoff-reuse-v1` retains the ship, sky, asteroid prototypes and batched ring-station geometry across levels. Previously those were synchronously rebuilt on every view creation despite the campaign packet cache. Scenery placements still follow the new track. `view-created` records `reusedSharedAssets`; scenery includes `reusedPrototypes`, `layoutMs`, `prototypeGenerationMs` (the initial cost), and `generationMs` (work for this view). `previous-view-disposed` and `start-first-render` isolate teardown and initial render submission. These identify remaining transition costs; packet preloading does not mean all level geometry is already uploaded to the GPU.

The next-level cache and generated level-buffer counters distinguish staged data from attached scene inventory. Indexed-buffer saving compares the stored attributes/indices against expanding the same geometry into independent triangle vertices; it does not claim reduced triangle counts or measured total VRAM. Worker build/attachment peaks now include current-level loading work (and worker builds include next-level preparation), since generation completes before driving. Capture FPS still excludes loading; compare the separate wait totals and events.

- **FPS / frame times:** uncapped requestAnimationFrame intervals. These are independent of simulation slow motion and the simulation's 60 ms delta clamp. Recent statistics cover up to 240 callbacks, including menus. Capture statistics cover active driving only, excluding paused/hidden-page intervals and the first resumed interval. FPS is frame count divided by elapsed time. p95 means 95% of retained intervals were at or below that duration. Lower is better; 60 FPS corresponds to 16.7 ms, 30 FPS to 33.3 ms.
- **Graph:** latest 240 intervals, clamped visually to 100 ms. Lines show 16.7 / 33.3 ms. Actual outliers remain uncapped in exports and statistics.
- **Calls / triangles / lines / points:** Three.js renderer counters for the latest scene render, after visibility and renderer culling. Draw calls are not scene mesh counts. These counters do not include intermediate environment-map generation passes. Repeated rendering during checkpoint handoff is timed in main CPU but the counters represent only the final scene render.
- **CPU timings:** main callback includes asset attachment/scheduling, simulation (and checkpoint setup), HUD, and view work. View includes guides/effects, camera/visibility changes, and render submission. These overlap and must not be added together. Main excludes diagnostic work, later browser layout/compositing, and asynchronous GPU execution. Render submission may include driver stalls, uploads, and shader compilation; it is not a GPU timer.
- **Asset builds:** campaign generation now runs in a worker. `workerBuildMs` and `workerPackMs` measure work on that separate thread and must not be added to main CPU time. `assetAttachMs` measures reconstruction from transferred buffers, environment binding, and scene attachment on the main thread. `assetPumpMs` also includes scheduling/readiness. Last worker build remains visible between jobs; position-tagged `worker-asset` events include build/pack/attachment costs. Initial view construction and run-start preparation have separate events, even if the panel is opened afterward. GPU upload/compile can still occur on first visibility.
- **Track waits:** if visible track or hazards are not ready, simulation and the race timer hold while the worker continues. The main thread keeps rendering and accepting pause/menu input. Driving FPS excludes these waits, so always compare the separate wait count/time alongside FPS; a higher FPS with long waits is not a satisfactory outcome. JSON includes wait events and totals, and CSV includes wait count/seconds. Counts/totals cover visible-page intervals while profiling, across the full capture (not only the retained driving frame window).
- **Memory:** renderer geometry/texture counts are resource counts, not bytes. CPU geometry bytes count distinct backing ArrayBuffers attached to scene geometry, including indices and morph attributes. They exclude driver allocations, textures, JS object overhead, detached caches and render targets. JS heap is a browser-provided estimate, available only on supporting browsers, and includes the profiler itself but not worker memory. Neither is total VRAM usage.
- **Inventory:** attached meshes, unique geometries/materials, light types, transparent material counts and material types. Hidden objects are included. Vertex counts sum unique geometry positions rather than submitted vertices. Chunk visibility counts the game visibility flag, before camera culling. Inventory and capture summary refresh every two seconds; other display fields refresh twice per second. Per-second exported samples are snapshots, not averages.
- **Diagnostics overhead:** measured separately and included in the next real frame interval, with last/max costs shown. The panel itself allocates memory and performs periodic scene scans/statistics. Use the reported overhead when interpreting small differences. It is inactive when closed, apart from run-start/construction event recording.

## Report retention

Reports retain the latest 18,000 driving frame records (about five minutes at 60 FPS), 900 one-second snapshots, and 500 events. Total recorded frames and retained counts make truncation explicit. Summary and per-level statistics use retained frames only. Save separate captures for device/level/mode comparisons.

Each frame interval is attached to the *previous* callback's workload, which delayed that interval. Slow-frame events over 50 ms therefore contain the matching preceding CPU and asset-build timings, level, distance, phase, and diagnostic overhead. This supports attribution but does not prove a bottleneck: browser scheduling, GC, GPU work and other applications can also delay callbacks. Export is intentionally excluded from frame intervals.

Source review and a production build are the agent's validation. Gameplay and device testing remain user-owned.
